# Phase 67 evidence-constrained static audit

> **Superseded by Phase 68.** The first Phase 67 cold boot reached stage 13
> but timed out waiting for Heat. The exact Windows trace was valid evidence,
> but replaying its collection/application setup in the Linux reset path was
> an invalid architectural assumption. See `PHASE68_PROVEN_RECOVERY.md`.

## Result

Phase 66 is not a valid cold-start implementation. On the target Surface it
completed stages 0 through 11, then timed out three times at stage 12. That
stage was a second report-09 A1/A5 pair copied from a later, partial KD recovery
capture. It does not occur in the complete ETW cold-start trace.

Phase 67 uses only the complete captured cold order:

1. device and report descriptors;
2. GetFeature `0x60`;
3. four OutputReport `0x65` exchanges;
4. GetFeature and SetFeature `0x70`;
5. SetFeature `0x56`;
6. GetFeature `0x06`;
7. one OutputReport `0x09` A1/A5 pair;
8. SetFeature `0x05`;
9. GetFeature `0x73`;
10. report-`0x12` Heat streaming.

The SetFeature `0x05` response is preceded by report `0xa0`; report `0x2e`
remains pending and is consumed while waiting for the subsequent feature
`0x73` response. The bounded response loop already implements that ordering.

## Version identity

The complete ETW trace uses report-09 profile bytes `1a 03`. Its OutputReport
`0x65` payload carries firmware bytes `89 14 00 3f`. The installed Microsoft
firmware INF independently identifies `FW_MSHW0485` version 63.20.137 as
`0x3F001489`. Phase 67 therefore refuses the Heat sequence with
`-EPROTONOSUPPORT` unless GetFeature `0x60` reports that exact firmware and
GetFeature `0x73` returns profile `1a 03`.

The later `14 03` value and second A1/A5 pair remain useful recovery evidence,
but they are not used in the production cold path because no complete capture
establishes their prerequisites.

## Defects corrected

- `g6ts_assign_tracks()` returned early when there were no existing tracks
  without initializing `contact_slots`. The caller then read indeterminate
  stack values. The first contact of a session could consequently be dropped,
  assigned to a nonexistent slot, or appear inconsistently. Every output slot
  is now initialized before any early return, with a static regression test.
- The unsupported Phase 66 post-SetFeature report pair was removed.
- Feature `0x73` now occurs before the first Heat-frame wait, exactly as in the
  complete trace.
- The installed firmware and report-09 profile are checked before touch is
  enabled instead of treating a partial-capture value as current configuration.
- The paired GENI DMA path now checks both `dmaengine_slave_config()` results,
  both DMA submission cookies, preserves `msg->status` on every early error,
  terminates both paired channels, and restores CPU DMA ownership and resting
  interrupt masks on setup failure.
- ACPI power-off/reset errors are propagated during initialization and suspend.
- A malformed indentation block in the QSPI event diagnostic path and missing
  doorbell barrier comments were corrected.

## Windows/Ghidra verification

No Microsoft binary is stored in this repository. The exact installed files
were mounted read-only and identified by SHA-256:

```text

TouchPenProcessor0C83.dll 615a28136f14678298dcd9f009c9295456a9e7ce878717b58d371d343b4c7132
```

Ghidra analysis of the installed `qcspi8380.sys` confirms:

- `FUN_14001b3c8` writes the same 13 GENI initialization registers represented
  by `spi_geni_sp11_qspi_prepare_hw()`;
- `FUN_140015e18` selects command 7 when TX and RX both exist, sets QSPI bit 29,
  puts only RX length in descriptor word 2, and emits base flag word
  `0x00200101`;
- live KD ring captures independently show CONFIG0 `03000004 00000000
  00010001 00220101` followed by GO `20000007 00000000 <rx_len> 00200101`.

Linux adds the GPI LINK flag to its bidirectional GO descriptor because the
Linux channel contexts are not implicitly paired like Microsoft's QGPI stack.
That is documented Linux integration policy, not claimed Windows code.

The checked-in classifier header was regenerated byte-for-byte from the exact
installed `TouchPenProcessor0C83.dll`; its SHA-256 is
`afdf32856750c50c6fb46694ae43dd1c48af17f96145766b11806f0bc15b17dc`.

## Boundary

This is the completed static/reverse-engineering audit for the exact target
kernel, panel firmware, and current Microsoft files. It is not a claim that a
newly corrected cold path has been hardware-validated: Phase 67 still requires
one isolated boot and touch/reset soak. Suspend/resume remains unvalidated on
this platform and pen support remains deliberately out of scope.

The audit also distinguishes exact facts from independently designed Linux
policy. The QSPI words, register masks, HID framing, cold sequence, firmware
identity, Heat parser, classifier coefficients, NSR mapping/cutoff, and
classifier output classes are backed by binary analysis and/or captures. The
GPI LINK bit, bounded recovery limits, 4096-unit association gate, coordinate
smoothing bands, and three/five/eight-frame confirmation windows are explicit
Linux policy. They are not presented as recovered Windows constants. Removing
that policy merely to claim byte-for-byte Windows parity would reintroduce
known ghost/split contacts; replacing it requires labelled captures or the
still-unrecovered initialized Windows tuning object.
